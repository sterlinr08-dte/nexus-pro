## 1. Mapa exacto del flujo actual

### 1.1 `_genFacturasInterno()` (`index.html:7012-7055`)

Genera facturas para TODOS los clientes elegibles de un período, en un `for` sobre el arreglo ya
cargado en memoria (`ST.clientes`). Por cada cliente:

1. Calcula `da = pend(c)` (deuda de facturas pendientes, sin incluir `deuda_anterior`) — el mismo
   cálculo que usa toda la app (`index.html:2905`).
2. Calcula `primaBase`/`primaDeps` con la lógica de precio especial/plan del cliente (fuera del
   alcance de este bloque, no se toca).
3. **Anti-duplicado — SOLO un `SELECT` seguido de un `INSERT`, sin ningún candado real entre los
   dos pasos**: comprueba si ya existe una factura no anulada de ese cliente para ese período
   consultando la BASE (no solo la memoria, eso ya se corrigió en v39.4 según CLAUDE.md) — pero
   entre el `SELECT` y el `INSERT` no hay ninguna transacción, ningún `FOR UPDATE`, ningún índice
   único que lo respalde. Dos invocaciones concurrentes de esta misma función (dos pestañas del
   mismo admin, o el timer `verificarAutoFacturacion()` disparándose en dos sesiones de usuario
   distintas el mismo minuto del día 20) pueden ambas pasar el chequeo antes de que ninguna haya
   comprometido su `INSERT`.
4. Llama a `generarNCF(tipo)` (`index.html:6365-6372`), que hace `API.post('rpc/siguiente_ncf', ...)`
   — esta parte SÍ es atómica (Bloque 2A, `UPDATE...RETURNING` con auto-creación de secuencia).
5. `API.post('facturas', {...})` — **INSERT directo a la tabla**, sin `origen`, sin
   `created_by_user_id`, sin `created_by_name` (esas 3 columnas existen en el esquema pero
   `_genFacturasInterno()` nunca las llena — confirmado con `grep`, cero apariciones de esos 3
   nombres en la función).
6. `API.patch('clientes', ..., {deuda_total: nuevo})` — suma la prima a la deuda del cliente.
7. **`API.post('asientos', {...})` — INSERT DIRECTO, sin `tipo_origen`, sin `origen_id`, sin
   `idempotency_key`.** Esta es la escritura directa que el objetivo de 3B busca eliminar.
8. Actualiza `ST.clientes[i]`/`ST.facturas` en memoria, incrementa un contador, sigue con el
   siguiente cliente del `for`.
9. Al terminar el `for`: `rFact()`, `rDash()`, `toast()` con el resumen.

No hay ninguna transacción que envuelva los pasos 3-7 para UN SOLO cliente, y mucho menos para el
lote completo — si el `INSERT` de `asientos` (paso 7) falla a mitad del lote, la factura y el
`deuda_total` del cliente YA quedaron comprometidos (pasos 5-6), sin ningún asiento contable que lo
respalde, y el `for` sigue con el siguiente cliente sin abortar ni avisar de forma visible (solo
pasa a la consola si acaso).

### 1.2 `anularFactura(facturaId)` (`index.html:7376-7416`)

1. Busca la factura en `ST.facturas` **en memoria** (no en la base) y valida
   `f.estado!=='Anulada'`/`f.estado!=='Pagado'` contra ese estado EN MEMORIA.
2. Chequeo de permiso client-side (`tienePermiso('editar_facturas')` o `sesion.rol==='admin'`).
3. `prompt()` nativo del navegador pidiendo el motivo (obligatorio).
4. `await API.patch('facturas', ..., {estado:'Anulada'})` — **PATCH directo, sin ninguna condición
   `WHERE estado NOT IN (...)` a nivel de base** (PostgREST solo filtra por `id=eq.<facturaId>`).
   Actualiza `f.estado` en memoria inmediatamente después, ANTES de que el resto del flujo corra.
5. **Bloque `try{}catch(eRev){console.warn(...)}` SEPARADO**: calcula `primaRev`, hace
   `API.patch('clientes', ..., {deuda_total: nuevaDeuda})`, luego
   `API.post('asientos', asiRev)` — **INSERT directo**, con una referencia derivada de
   `f.ncf.replace(/\D/g,'').slice(-4)` (últimos 4 dígitos del NCF, no un id único). Si CUALQUIERA
   de estas 2 escrituras falla, el `catch` solo hace `console.warn` — **invisible para el usuario**,
   que ya vio "Factura anulada" en el toast de éxito de más abajo, aunque la deuda y el asiento
   nunca se hayan revertido.
6. `try{recalcularSaldosContables();}catch(_){}` — **100% client-side/en memoria**, recorre
   `ST.asientos` para recalcular los saldos que se muestran en pantalla. No escribe nada a la base.
   Confirmado leyendo `index.html:3459-3474`.
7. **`try{await resyncEstadoFacturas(f.cliente_id);}catch(e){}` — un `await` SEPARADO, DESPUÉS de
   todo lo anterior, con un `catch` completamente vacío (ni siquiera `console.warn`).** Esta es la
   función que reparte `clientes.pagado` oldest-first sobre las facturas no anuladas del cliente
   (`_saldoFacturasCliente`, `index.html:7075-7100`) y corrige el `estado` cacheado de las facturas
   hermanas. Si esta llamada falla (red, timeout, lo que sea), **ninguna factura hermana se
   resincroniza y nadie se entera** — es el mismo tipo de bug que ya se documentó y arregló una vez
   en CLAUDE.md (v49.95/v49.96) para `nxEditarPrecioFactura`, pero AQUÍ sigue sin cerrar.
8. `logAudit('FACTURA_ANULADA', ...)` — client-side, hace su propio `API.post('auditoria', ...)`.
9. `rFact()`, `rDash()`, `toast('ok', ...)`.

### 1.3 Lo que queda frontend / post-commit (no entra a la transacción)

- El `prompt()` del motivo (UI, no puede vivir en SQL).
- El chequeo de permiso client-side (se mantiene como primera línea de defensa en UX, pero deja de
  ser la única barrera real — la RPC lo re-verifica server-side).
- `recalcularSaldosContables()` (puramente en memoria, no toca la base).
- Repintado (`rFact()`, `rDash()`) y `toast()`.
- El `for` que recorre TODOS los clientes elegibles del período en `_genFacturasInterno()` — la
  RPC nueva atiende UN cliente por llamada; el lote lo sigue coordinando el frontend, llamando la
  RPC una vez por cliente (ver sección 3).

## 2. Riesgos actuales

### CRÍTICO

- **C1 — Anulación no atómica, con reversión contable silenciosamente saltable.** El `PATCH` de
  `facturas.estado='Anulada'` se compromete y confirma al usuario ANTES de que la reversión de
  `deuda_total` y el asiento de reversa siquiera se intenten — y si esos 2 pasos fallan, el único
  rastro es un `console.warn` que nadie ve. Una factura puede quedar marcada "Anulada" en la base
  con su deuda TODAVÍA sumada al cliente y SIN ningún asiento de reversa — descuadre contable real,
  invisible, sin ninguna alerta.
- **C2 — Resync de facturas hermanas puede fallar en total silencio.** `catch(e){}` vacío tras
  `resyncEstadoFacturas`. Si falla, las facturas hermanas del cliente quedan mostrando un estado
  (Pendiente/Parcial/Pagado) que ya no corresponde a la realidad — el mismo bug de fondo que
  CLAUDE.md ya documentó y cerró para 2 de los 3 flujos que tocan este reparto (v49.95/v49.96,
  `nxEditarPrecioFactura`/`anularFactura` vía `resyncEstadoFacturas`), pero el 3er flujo
  (`anularFactura` en sí) sigue con el mismo patrón fràgil que motivó ese arreglo.
- **C3 — Race de doble-factura sin candado real (TOCTOU).** El anti-duplicado de
  `_genFacturasInterno()` es lectura-y-luego-escritura sin transacción ni índice único de por
  medio. Con el timer `verificarAutoFacturacion()` corriendo cada minuto EN CADA sesión abierta
  (`index.html:~10820-10841`) y el día 20 disparando el mismo cliente en simultáneo desde varios
  navegadores/pestañas de distintos usuarios logueados, dos facturas para el mismo cliente/período
  pueden comprometerse ambas — doble cobro real al cliente, cada una con su propio NCF válido (el
  NCF en sí no se duplica, pero el cliente ve 2 facturas legítimas del mismo mes).
- **C4 — Sin control de rol real en ninguno de los 2 flujos.** Ninguna de las 2 funciones
  comprueba nada del lado del servidor — el único gate es `tienePermiso('editar_facturas')`
  (client-side, en `roles_perms`, editable desde `localStorage`/la propia sesión del navegador) o
  `sesion.rol==='admin'` (también solo en memoria del cliente). Confirmado leyendo `roles_perms`
  real de producción (ver sección 5) que el permiso `editar_facturas` HOY está asignado también al
  rol `agente`, no solo `admin` — así que, en el sistema actual, un agente logueado (Robinson) ya
  puede anular facturas y no hay forma de impedirlo del lado del servidor.

### ALTO

- **A1 — `_genFacturasInterno()` no es transaccional dentro de un mismo cliente.** Factura +
  `deuda_total` + asiento son 3 escrituras REST separadas para el MISMO cliente; si la 3ª (el
  asiento) falla, las primeras 2 ya se comprometieron.
- **A2 — Sin idempotencia real en ninguno de los 2 flujos.** Un doble-click en "Generar factura" o
  en "Anular" reintenta la operación completa desde cero — nada impide procesar la misma intención
  dos veces si el primer intento se quedó a medias (ej. timeout de red justo después del `INSERT`
  de la factura pero antes de confirmar al usuario).
- **A3 — Referencia de la anulación derivada de 4 dígitos del NCF, no de un id único.** `'AST-ANUL-'
  + últimos 4 dígitos del NCF` puede colisionar entre NCF de secuencias distintas que terminen en
  los mismos 4 dígitos — no rompe nada hoy porque nadie más lee esa referencia con precisión, pero
  es una debilidad de trazabilidad.

### MEDIO

- **M1 — `facturas.origen`/`created_by_user_id`/`created_by_name` nunca se llenan.** Existen 103
  filas históricas con `origen='MANUAL'` (backfill de una sesión pasada, no de código vivo — cero
  lecturas de `.origen` en todo `index.html`, confirmado con `grep`), pero ninguna factura generada
  HOY por `_genFacturasInterno()` deja rastro de quién la generó ni de que fue manual.
- **M2 — Un `$0` de factura, tras pasar por el reparto oldest-first, se etiqueta "Pagado" aunque
  nunca se le haya pagado nada.** Propiedad matemática del propio algoritmo (`saldo<=0.009` es
  cierto cuando `total=0` y `saldo=0`) — inherente al algoritmo YA EXISTENTE (`resyncEstadoFacturas`/
  `_saldoFacturasCliente`), no algo que 3B introduzca; se documenta porque se topó con él durante
  las pruebas (ver sección 8) y conviene que quede escrito, aunque es inofensivo en la práctica (una
  factura de $0 no tiene nada que cobrar sin importar cómo se etiquete).

## 3. Arquitectura propuesta y justificación

**Se comparó contra `crear_factura_auto_tx` (la RPC ya existente que usa el cron de
auto-facturación) y se descartó reutilizarla o endurecerla directamente.** Es
`service_role`-only, sin ningún guardia de rol/organización (su único caller de hoy es el propio
cron, un contexto ya confiable) — abrirle un camino interactivo desde el frontend, aunque fuera con
un guardia nuevo, mezclaría dos superficies de confianza muy distintas (un proceso automatizado sin
sesión de usuario vs. un clic real de un admin logueado) dentro de la misma función. Se eligió, en
su lugar, **crear 2 RPCs hermanas nuevas**, mismo patrón exacto que las 2 de Bloque 3A
(`seguros_registrar_asiento_manual`/`seguros_corregir_asiento_manual`): guardia de rol/organización
explícito, idempotencia real, transaccional de punta a punta, sin tocar ni una línea de
`crear_factura_auto_tx` (que sigue intacta, sirviendo solo al cron).

- **`seguros_generar_factura_manual(...)`** — **atiende UN cliente por llamada**, no un lote. Se
  descartó una RPC "de lote" que reciba un arreglo de clientes: una sola llamada larga que procese
  N clientes en una sola transacción arriesga dejar TODO el lote bloqueado/abortado si UN cliente
  falla (ej. un cliente inactivo en medio del lote), y una transacción de minutos sobre `clientes`/
  `facturas` competiría mal con cobros/otras escrituras concurrentes. El frontend sigue coordinando
  el `for` sobre los clientes elegibles (eso ya lo hace bien, es lógica de negocio de "quién es
  elegible este período" que no vale la pena mover al servidor), pero cada iteración del `for` pasa
  a ser una llamada atómica independiente a esta RPC en vez de 3 escrituras REST sueltas.
- **`seguros_anular_factura(...)`** — une en UNA transacción lo que hoy son 4 pasos separados y sin
  candado (estado de la factura, reversión de `deuda_total`, asiento de reversa, resync de las
  facturas hermanas) — cierra C1 y C2 de raíz, no con un mejor manejo de errores del lado del
  cliente sino haciendo que sea IMPOSIBLE que la factura quede "Anulada" sin su reversión contable
  y su resync: o las 4 cosas pasan juntas, o ninguna.
- **El precio (`prima_base`/`prima_deps`) SIGUE calculándose en el frontend** con la misma lógica
  de hoy (plan del cliente, precio especial, dependientes) y se manda como parámetro — exactamente
  el mismo nivel de confianza que `crear_factura_auto_tx` ya tiene HOY con el cron (que recibe sus
  montos ya calculados por la Edge Function). No es una regresión de seguridad frente al status
  quo: mover ese cálculo al servidor sería un cambio de mayor alcance (reimplementar toda la lógica
  de precios/planes en PL/pgSQL) que no aporta al objetivo real de 3B (cerrar la escritura directa
  de `asientos`), y no fue pedido. **Lo que SÍ se movió al servidor porque es barato y cierra un
  hueco real:** `deuda_ant` SIEMPRE se recalcula dentro de la RPC contra `clientes.deuda_total`/
  `pagado` FRESCOS (con `FOR UPDATE`), nunca se acepta como parámetro del cliente — ni siquiera
  existe un `p_deuda_ant` en la firma.

## 4. Definición exacta de las RPCs propuestas

**El SQL completo, línea por línea, está en `docs/bitacora/2026-08-12-1418-propuesta-3b-NO-APLICAR.sql`
(archivo separado, marcado NO APLICAR, en este mismo commit).** Resumen de lo que contiene:

1. **Migración aditiva** — `CREATE UNIQUE INDEX IF NOT EXISTS facturas_cliente_periodo_activa_unico
   ON facturas(cliente_id, periodo) WHERE estado <> 'Anulada'` — verificado ANTES de proponerlo que
   la base real de producción **no tiene ningún conflicto hoy** (`SELECT cliente_id, periodo,
   count(*) FROM facturas WHERE estado<>'Anulada' GROUP BY 1,2 HAVING count(*)>1` → 0 filas), así
   que el índice se podría crear sin fricción. Cierra C3 a nivel de base — el candado real no es el
   pre-chequeo dentro de la RPC (ese solo da un mensaje amable en el caso común), es este índice.
2. **`seguros_generar_factura_manual(p_cliente_id, p_periodo, p_mes, p_anio, p_prima_base,
   p_prima_deps, p_tipo_ncf, p_fecha_emision, p_idempotency_key) RETURNS jsonb`** —
   `SECURITY INVOKER`, `SET search_path TO 'public','pg_temp'` (mismo patrón que las 2 de 3A, sin
   declarar `SECURITY DEFINER` — corre con los privilegios del llamador real, así que las tablas
   subyacentes siguen protegidas por RLS/grants de forma independiente al guardia explícito). Orden
   interno: guardia rol/org → candado de idempotencia (`pg_advisory_xact_lock` +
   `SELECT...WHERE idempotency_key=...`, reusa el mismo índice único `asientos.idempotency_key`
   creado en 3A, sin migración nueva para esto) → validación de entrada → lectura bloqueada
   (`FOR UPDATE`) y fresca del cliente → pre-chequeo de duplicado (mensaje amable) →
   `deuda_ant`/`total` recalculados server-side → `siguiente_ncf()` (reusado, no reimplementado) →
   `INSERT facturas` (con `origen='MANUAL'`, `created_by_user_id`, `created_by_name` — cierra M1) →
   `UPDATE clientes.deuda_total` → `INSERT asientos` con `tipo_origen='factura_manual'`,
   `origen_id=<factura_id>`, `idempotency_key` → `INSERT auditoria` (con `cliente_id` poblado).
3. **`seguros_anular_factura(p_factura_id, p_motivo, p_idempotency_key) RETURNS jsonb`** — mismo
   perfil de seguridad. Guardia rol/org → candado de idempotencia → **el primitivo atómico real:
   `UPDATE facturas SET estado='Anulada' WHERE id=... AND estado NOT IN ('Anulada','Pagado')
   RETURNING *`** (ni un `SELECT` previo ni un `f.estado` en memoria del navegador deciden si se
   puede anular — lo decide la propia base, en el mismo statement que hace el cambio) → si
   `rows_affected=0`, relee el estado real y devuelve `{ok:true,reintento:true}` (ya estaba
   anulada) o `RAISE EXCEPTION` (Pagado, o cualquier otro estado no anulable) → si sí se pudo
   anular: reversión de `deuda_total`, `INSERT asientos` con `tipo_origen='reversa_factura'`,
   `origen_id=<factura_id>` (cierra C1), y **el mismo algoritmo de reparto oldest-first de
   `resyncEstadoFacturas`/`_saldoFacturasCliente` PORTADO a PL/pgSQL, corriendo dentro de la MISMA
   transacción** (cierra C2 — nunca puede fallar "aparte", o corre junto con todo lo demás o no
   corre nada) → `INSERT auditoria`.
4. `REVOKE ALL ... FROM PUBLIC/anon; GRANT EXECUTE ... TO authenticated, service_role;` para las 2,
   idéntico al patrón de 3A.

**Consistencia con convenciones reales verificadas antes de escribir, no asumidas:**
`asientos.tipo_origen='reversa_factura'`/`'factura_manual'` son namespaces NUEVOS que no chocan con
los que ya usa 3A (`'manual'`/`'manual_reversa'`) — confirmado que el blindaje de 3A
(`seguros_corregir_asiento_manual` rechaza cualquier `tipo_origen NOT IN ('manual','manual_reversa')`)
sigue protegiendo a los asientos de 3B sin tocar 3A. `asientos.cliente_id`/`asientos.factura_id`
(2 columnas que existen en el esquema) se dejan SIN poblar en las 2 RPCs nuevas — confirmado leyendo
`crear_factura_auto_tx` y las 2 RPCs de 3A que NINGUNA de ellas las usa tampoco; el enlace real es
siempre `tipo_origen`+`origen_id`, y 3B sigue esa misma convención en vez de inventar una nueva.
`facturas.origen='MANUAL'` (mayúscula) en vez de `'manual'` — se verificó contra la base real
(`SELECT origen, count(*) FROM facturas GROUP BY 1` → 103 filas con `'MANUAL'`, 0 con cualquier otra
variante) antes de fijar el literal.

## 5. Matriz actor × operación

Se auditó `configuracion.roles_perms` REAL de producción antes de recomendar nada:
`editar_facturas` está asignado hoy a `admin` **y a `agente`**. O sea, en el sistema actual, un
agente logueado (Robinson, en nexus-pro) ya puede anular una factura desde la UI, sin ningún gate
server-side que lo detenga. ChatGPT pidió explícitamente NO asumir que porque el botón sea
alcanzable hoy por agente eso deba conservarse.

| Operación | admin nexus-pro | agente nexus-pro | admin cross-org | anon | service_role (sin JWT) | service_role (impersonando admin) |
|---|---|---|---|---|---|---|
| `seguros_generar_factura_manual` | ✅ permitido | ❌ rechazado (rol) | ❌ rechazado (org) | ❌ rechazado (grant, 42501) | ❌ rechazado (rol, `mi_rol()` nulo) | ✅ permitido |
| `seguros_anular_factura` | ✅ permitido | ❌ rechazado (rol) | ❌ rechazado (org) | ❌ rechazado (grant, 42501) | ❌ rechazado (rol, `mi_rol()` nulo) | ✅ permitido |

**Recomendación: mínimo privilegio real = `admin` únicamente para las 2 operaciones, sin importar
lo que diga hoy `roles_perms`.** Emitir una factura manual "genera" dinero por cobrar contra un
cliente y anular una factura revierte dinero comprometido — son las 2 operaciones de mayor impacto
financiero directo del módulo de Facturas, en la misma categoría que "corregir/registrar un asiento
manual" (que 3A YA restringió a admin-only sin que nadie lo objetara). No se encontró ningún caso de
uso operativo real documentado en CLAUDE.md donde un agente necesite generar o anular facturas por
su cuenta (los agentes cobran y registran abonos — `seguros_registrar_cobro`, otro flujo, ya
propio — no facturan). El costo de restringir a admin: si algún negocio SÍ delega esto a un agente
de confianza hoy, perdería la capacidad hasta que el dueño se lo pida explícitamente y se abra un
camino aparte (ej. un permiso nuevo `facturar_manual`/`anular_facturas` separado de
`editar_facturas`, en vez de reusar el mismo permiso genérico que hoy cubre demasiado). Esto se
señala aquí, no se decide unilateralmente — es justo el tipo de llamada que ChatGPT pidió no asumir
en automático.

**`service_role` con y sin impersonación** se prueban por completitud (punto 9 de la autorización)
aunque hoy no hay ningún llamador legítimo de `service_role` para estos 2 flujos (a diferencia de
`crear_factura_auto_tx`, que SÍ tiene un llamador real: el cron). El GRANT a `service_role` se deja
por consistencia con el patrón ya establecido en 3A, con el guardia de rol interno actuando como
segunda capa: un `service_role` "pelado" (sin `request.jwt.claims`) queda rechazado igual que
cualquier otro caller sin identidad admin — nunca hay un camino que salte el chequeo de rol.

## 6. Estrategia de idempotencia

**Doble candado, no uno solo:**

1. **Clave de idempotencia explícita** (`p_idempotency_key`, generada en el frontend con
   `nxNuevaIdemKey()`, el mismo helper ya usado por 3A) — `pg_advisory_xact_lock` +
   `SELECT...WHERE idempotency_key=...` sobre `asientos`, reusando el ÍNDICE ÚNICO
   `asientos_idempotency_key_uq` ya creado en 3A. Un reintento con la MISMA clave (doble-click en el
   mismo intento, o un reintento automático tras un timeout de red) devuelve
   `{ok:true,reintento:true,...}` con los ids ya comprometidos, sin duplicar factura/asiento/deuda.
2. **Para la anulación, además — y esto es el candado MÁS FUERTE, más allá del anterior — el propio
   estado de la factura es su propio candado, sin necesitar una clave compartida.** El
   `UPDATE...WHERE estado NOT IN ('Anulada','Pagado')` hace que un SEGUNDO intento de anular la
   MISMA factura, aunque venga con una clave de idempotencia DISTINTA (dos pestañas distintas, cada
   una generando su propia clave al azar — el escenario real de "doble-click en dos ventanas"), sea
   detectado y devuelto como `{ok:true,reintento:true,nota:'La factura ya estaba anulada'}` sin
   volver a revertir la deuda ni duplicar el asiento — **probado explícitamente** (ver escenario O
   en la sección 8).

Para la generación, el equivalente de "el estado es su propio candado" es el **índice único**
`facturas_cliente_periodo_activa_unico`: dos intentos de generar la MISMA factura con claves de
idempotencia DIFERENTES (no solo el mismo reintento con la misma clave) chocan contra el índice, no
contra la clave — probado en el escenario E (INSERT crudo, bypaseando la RPC por completo, para
simular la peor condición de carrera posible).

## 7. `SECURITY INVOKER`, `search_path`, grants — cómo queda todo listo para 3C

- Las 2 RPCs son `SECURITY INVOKER` (igual que las 2 de 3A, igual que `crear_factura_auto_tx`) —
  corren con los privilegios REALES del llamador. Esto significa que, cuando en 3C se retire
  `INSERT`/`UPDATE` directo a `asientos` para `authenticated` (cerrando la política `all_asientos`
  global), estas 2 RPCs **seguirán funcionando exactamente igual**: el `INSERT INTO asientos` que
  hacen por dentro seguirá pasando por las mismas políticas RLS que le apliquen a `authenticated`
  en ese momento — la única diferencia real es que HOY un usuario `authenticated` cualquiera
  también podría insertar en `asientos` DIRECTO (sin pasar por ninguna RPC), y en 3C ya no podría —
  las RPCs, al ser `SECURITY INVOKER`, no necesitan ningún permiso especial para seguir
  funcionando, porque el guardia real de "quién puede insertar un asiento de este tipo" ya vive
  DENTRO de la función (`mi_rol()='admin'`), no en la política RLS de la tabla.
- `SET search_path TO 'public','pg_temp'` en las 2 — mismo patrón defensivo que 3A (evita que un
  objeto malicioso en un schema anterior en el `search_path` por defecto de la sesión intercepte
  una referencia sin calificar).
- `siguiente_ncf()` (que la RPC de generación llama por dentro) es `SECURITY DEFINER` con su PROPIO
  guardia interno (`auth.role() IS DISTINCT FROM 'service_role' AND session_user <> 'postgres'` →
  exige `mi_rol()` no nulo + organización nexus-pro) — como mi nueva RPC ya exige admin+nexus-pro
  ANTES de siquiera llegar a llamar a `siguiente_ncf()`, el guardia de `siguiente_ncf()` se satisface
  trivialmente (admin nexus-pro implica rol no-nulo + org correcta) — no hay conflicto ni doble
  validación redundante que rompa nada.
- **Hipótesis investigada y descartada, para que quede escrito con honestidad:** se sospechó
  inicialmente una posible carrera entre el candado de `crear_factura_auto_tx` (`SELECT...FOR
  UPDATE` sobre `secuencias_ncf`) y el de `siguiente_ncf()` (lock implícito de un `UPDATE`) por usar
  mecanismos de bloqueo distintos. Se leyó el `pg_get_functiondef` real de ambas y se confirmó que
  los DOS toman un lock de FILA sobre la MISMA fila de `secuencias_ncf` (uno explícito, uno
  implícito) — en Postgres, cualquier lock de fila, sin importar el mecanismo que lo pida, serializa
  correctamente contra cualquier otro lock de fila sobre la misma fila. No hay carrera real; se
  descarta la hipótesis.

## 9. Cambios frontend exactos que 3C necesitaría (descritos, NO aplicados)

Mismo idioma ya establecido por la migración de 3A (`guardarAsientoFn()`,
`index.html:9110-9159`) — `API.post('rpc/<función>', {p_param: valor, ...})`, variable de módulo
`_xxxIdemKey` renovada tras cada éxito, `nxRpcErr(e)` para el mensaje de error, refetch puntual de
la fila real (no un merge ciego del payload que se mandó) antes de repintar.

**`_genFacturasInterno()`** — el `for` sobre clientes elegibles se mantiene íntegro; dentro del
`for`, en vez de los pasos 5-7 actuales (INSERT factura / PATCH cliente / INSERT asiento, sueltos),
una sola llamada:
```js
const idem = nxNuevaIdemKey();
const r = await API.post('rpc/seguros_generar_factura_manual', {
  p_cliente_id: c.id, p_periodo: periodo, p_mes: mes, p_anio: anio,
  p_prima_base: primaBase, p_prima_deps: primaDeps, p_tipo_ncf: tipoNcf,
  p_fecha_emision: hoy(), p_idempotency_key: idem
});
if (r && r.ok === false) { /* ya existía, se salta este cliente sin contar como error */ continue; }
if (!r || !r.ok) throw new Error('La RPC no confirmó la factura');
// refetch puntual de la factura real (mismo patrón que guardarAsientoFn) y merge en ST.facturas/ST.clientes
```
Al final del `for`, igual que hoy: `rFact()`, `rDash()`, `toast()` con el resumen del lote.

**`anularFactura(facturaId)`** — se conserva el `prompt()` del motivo y el chequeo client-side de
permiso (como primera línea de UX, ya no como única barrera). El bloque de escritura completo
(hoy: `PATCH facturas` + `try{PATCH clientes + POST asientos}catch` + `try{recalcularSaldosContables}`
+ `try{resyncEstadoFacturas}catch{}` + `logAudit`) se reemplaza por:
```js
const idem = nxNuevaIdemKey();
const r = await API.post('rpc/seguros_anular_factura', {
  p_factura_id: facturaId, p_motivo: motivo.trim(), p_idempotency_key: idem
});
if (!r || !r.ok) throw new Error('La RPC no confirmó la anulación');
// refetch puntual de la factura + del cliente (para deuda_total actualizado) desde la base
// recalcularSaldosContables() se mantiene (sigue siendo puro cálculo en memoria sobre ST.asientos)
rFact(); if (typeof rDash === 'function') rDash();
toast('ok', 'Factura anulada', ...);
```

`logAudit(...)` client-side deja de ser necesario para ESTA acción específica — la RPC ya escribe

   columna nueva se agrega (`facturas.origen`/`created_by_*` YA EXISTÍAN antes de 3B, solo estaban

   momento de esta auditoría y el momento en que se aplique de verdad apareciera un duplicado real
   en producción (alguien generó 2 facturas del mismo cliente/período por fuera de este flujo), el
   `CREATE UNIQUE INDEX` fallaría al crearse — mitigación: re-correr la consulta de verificación

4. **Nada de esto toca `all_asientos`** — si 3B se revierte por completo, el estado de RLS de
   `asientos` queda exactamente como lo dejó 3A, sin ningún cambio adicional que deshacer ahí.
