## Guía obligatoria para Claude — creación, aprobación y activación de plantillas WhatsApp en NEXUS PRO

### Motivo de esta bitácora

El dueño pidió dejar por escrito el flujo correcto porque se está confundiendo **crear una plantilla en Meta/Zernio** con simplemente agregar su nombre al código.

En NEXUS PRO son pasos distintos:

1. Diseñar el contenido y las variables.
2. **Someter la plantilla real a Meta por Zernio.**
3. Esperar y comprobar estado real `APPROVED`.
4. Solo después conectar esa plantilla al flujo/automatización que la usará.
5. Probar el envío real sin alterar datos financieros.

**Agregar un string como `reporte_novedades_ciclo_v1` en JavaScript/TypeScript NO crea una plantilla en Meta.**

## 1. Infraestructura actual que YA existe y debe usarse

### Crear/someter una plantilla nueva

Edge Function existente:

`supabase/functions/whatsapp-plantilla-crear/index.ts`

Esta función:

- recibe la solicitud desde una sesión autorizada de NEXUS PRO;
- resuelve internamente el `zernio_account_id` activo;
- mantiene `ZERNIO_API_KEY` únicamente del lado servidor;
- llama realmente a:

`POST https://zernio.com/api/v1/whatsapp/templates`

Payload base:

```json
{
  "accountId": "...",
  "name": "nombre_plantilla",
  "category": "UTILITY",
  "language": "es",
  "components": [...]
}
```

Categorías permitidas por la función actual:

- `AUTHENTICATION`
- `UTILITY`
- `MARKETING`

Para los reportes operativos de NEXUS PRO usar normalmente `UTILITY`, salvo que el contenido real obligue a otra categoría.

### Regla crítica de variables

Si el texto contiene `{{1}}`, `{{2}}`, etc., Meta requiere ejemplos.

El body debe incluir:

```json
{
  "type": "body",
  "text": "Hola {{1}} ...",
  "example": {
    "body_text": [
      ["EJEMPLO 1", "EJEMPLO 2"]
    ]
  }
}
```

Los ejemplos deben corresponder **exactamente en cantidad y orden** con las variables.

Usar datos ficticios en los ejemplos. No mandar cédulas reales de clientes a Meta como ejemplos.

## 2. Consultar el estado real de las plantillas

Edge Function existente:

`supabase/functions/whatsapp-plantillas-gestionar/index.ts`

Acción:

`accion: "listar"`

Permite filtrar por:

- `estado`
- `nombre`
- `idioma`

Internamente consulta:

`GET https://zernio.com/api/v1/whatsapp/templates?accountId=...`

### Regla obligatoria

**Nunca afirmar que una plantilla está aprobada por tiempo transcurrido o porque fue creada correctamente.**

Una creación correcta normalmente puede devolver `PENDING`.

Antes de decir al dueño “Meta la aprobó”, hacer una consulta fresca y confirmar literalmente:

`status = "APPROVED"`

Si devuelve:

- `PENDING`: sigue en revisión.
- `REJECTED`: no conectar a producción; revisar motivo/contenido.
- `APPROVED`: ya se puede integrar al flujo real.

## 3. Enviar una plantilla aprobada

La misma función:

`whatsapp-plantillas-gestionar`

tiene:

`accion: "enviar"`

Antes de enviar, vuelve a validar contra Zernio que la plantilla exista con:

- nombre exacto;
- idioma exacto;
- `status = APPROVED`.

Luego usa el endpoint real de conversaciones de Zernio.

No saltarse esta validación.

## 4. Flujo correcto de trabajo para cualquier plantilla nueva

Claude debe seguir este orden:

### A. Diseñar

Definir:

- nombre estable en `snake_case`;
- categoría;
- idioma;
- texto exacto;
- variables numeradas consecutivamente;
- ejemplos ficticios;
- destinatario;
- evento que dispara el mensaje;
- reglas para evitar duplicados.

### B. Someter

Usar `whatsapp-plantilla-crear`.

Guardar en una nueva bitácora:

- nombre exacto;
- texto exacto sometido;
- categoría;
- idioma;
- variables;
- ID devuelto por Meta/Zernio si existe;
- estado devuelto al crear (`PENDING`, etc.).

### C. Esperar y verificar

Usar `whatsapp-plantillas-gestionar` → `listar`.

No modificar la automatización productiva mientras esté `PENDING`.

### D. Activar

Solo con `APPROVED`:

- conectar el nombre real de la plantilla al Edge Function/trigger/cron correspondiente;
- respetar exactamente el orden de parámetros;
- desplegar la función que cambió;
- dejar bitácora de la activación;
- hacer prueba controlada.

### E. Probar

Preferir el número del administrador/dueño para una prueba real.

No crear pagos, facturas o movimientos financieros falsos únicamente para disparar el mensaje.

Registrar diferencia entre:

- `enviado`: Zernio aceptó el mensaje;
- `entregado`: confirmado como entregado;
- `leído`: confirmado como leído.

No usar “enviado” como sinónimo de “leído”.

## 7. Próxima plantilla: reporte de NOVEDADES del ciclo

Todavía no asumir que existe en Meta solo porque se haya hablado de ella.

Nombre de trabajo propuesto:

`reporte_novedades_ciclo_v1`

**No marcarla como creada, pendiente o aprobada hasta que se someta realmente y la API de Zernio lo confirme.**

La fuente de datos será el nuevo módulo **Novedades** de Clientes.

### Estructura funcional definida por el dueño

“Novedades” sustituye el antiguo concepto separado de “En proceso” para evitar ventanas repetidas.

Debe incluir como acápites principales:

- **ENTRADA**
- **SALIDA**

También debe conservar los casos que estén en gestión/proceso hasta que sean resueltos.

### Automatización de SALIDA

Cuando un cliente acumule **dos meses juntos pendientes**, el sistema debe seleccionarlo automáticamente en **Novedades → Salida** como caso para revisión/seguimiento.

Esto significa:

- crear/marcar automáticamente la novedad de salida;
- mostrarla en el listado y en el reporte;
- **NO dar de baja automáticamente al cliente del seguro**;
- la salida real requiere confirmación humana;
- si el caso se resuelve/paga, debe dejar de aparecer como salida pendiente y quedar trazabilidad/historial.

Evitar duplicar la misma novedad cada vez que corra la automatización: debe existir idempotencia por cliente + tipo + estado/ciclo según el diseño final.

### ENTRADA

Debe agrupar clientes que necesitan entrar/activarse en el seguro y los casos asociados que todavía estén pendientes de gestión.

### Reporte de novedades

La futura plantilla debe responder principalmente:

**“¿Qué novedades siguen pendientes de resolver en este ciclo?”**

Debe poder incluir, según el diseño final aprobado:

- entradas pendientes;
- entradas/en gestión;
- salidas detectadas por 2 meses juntos pendientes;
- salidas por confirmar;
- cantidad total de novedades abiertas;
- nombre y cédula cuando corresponda;
- motivo/estado y días pendiente si el dato está disponible.

Los casos resueltos deben pasar a historial y dejar de aparecer como pendientes en el siguiente reporte.
