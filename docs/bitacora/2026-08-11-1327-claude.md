### 2) Definición actual vs. propuesta, por función

Los 5 cuerpos exactos (actual y propuesto) y sus GRANT/REVOKE viven completos en
`docs/bitacora/subfase-2a-hardening-rpc-fiscales.sql` — aquí solo el resumen y el porqué de
cada uno, con el USO REAL confirmado por grep en `index.html`/`parches.js` (no supuesto):

**1. `siguiente_ncf(text)`** — USO REAL: único llamador es `generarNCF(tipo)` desde
`_genFacturasInterno()`, alcanzable por el botón "Generar" de Facturas SIN gate de rol
(`ROLES_PERMS.agente` incluye `ver_facturas`). **Guard: cualquier rol de `nexus-pro`** (admin O
agente) — restringir a solo-admin rompería ese botón que agentes usan hoy sin problema.
REVOKE de `anon` = NO-OP verificado (ya lo tenía revocado). El fix real es el guard interno.

**2. `next_recibo()`** — USO REAL: **cero llamadores** en el frontend (grep exhaustivo de
`rpc/next_recibo` con límite de palabra — solo `next_recibo_anio` se usa). Se le aplica el
MISMO guard que a `next_recibo_anio` por consistencia de familia, en vez de revocar EXECUTE
del todo (deja abierta la recuperación futura desde una sesión real de `nexus-pro` si algún día
hace falta, y de cualquier forma queda denegada a cross-org/anon, que es lo que importa).

**3. `next_recibo_anio(int)`** — USO REAL: llamada desde `asignarNumeroRecibo()` en
`parches.js` (~línea 15938), dentro del modal "Registrar abono" — se dispara CADA VEZ que
cualquier usuario (admin o agente) registra un cobro en Seguros. Funcionalidad diaria real de
un agente (Robinson). Mismo guard que 1: cualquier rol de `nexus-pro`.

**4. `crear_factura_auto_tx(...)`** — USO REAL: **cero llamadores** desde el frontend; el único
llamador legítimo es la Edge Function `auto-facturacion`, confirmado leyendo su código fuente
(`Deno.env.get("SUPABASE_SERVICE_ROLE_KEY")` + `supabase.rpc("crear_factura_auto_tx",...)`) —
toda llamada legítima llega como `service_role`. **Es la ÚNICA de las 5 donde `anon` sí tiene
EXECUTE abierto hoy de verdad** (`has_function_privilege('anon',...)` → `true`, confirmado). No
necesita guard interno — basta con cerrar el GRANT excesivo (era `anon+PUBLIC+authenticated` por
copy-paste, el hallazgo ALTO #6 de la auditoría Fase 2). Cuerpo de la función **100% intacto**
— cero riesgo sobre la lógica transaccional de facturación (anti-duplicado + NCF + asiento).
Detalle adicional confirmado: la función es `SECURITY INVOKER` (no DEFINER — `prosecdef=false`),
así que corre con la RLS del que llama contra `secuencias_ncf`; eso ya la protegía parcialmente
en la práctica (ver prueba en §4), pero el EXECUTE abierto seguía siendo una superficie de
ataque innecesaria.

**5. `seguros_diagnostico_financiero()`** — USO REAL: **cero llamadores** en el frontend, solo
invocada manualmente vía MCP durante Fase 1/Fase 2 como diagnóstico. Regla explícita #5 de
ChatGPT: restringida a **admin** de `nexus-pro` (no "cualquier rol", a diferencia de 1-3).
REVOKE de `anon` = NO-OP verificado. El fix real es el guard interno admin-only.

**Mecanismo del guard (funciones 1, 2, 3, 5):**

```sql
if auth.role() is distinct from 'service_role' and session_user <> 'postgres' then
  if mi_rol() is null or mi_organizacion() is distinct from
     (select id from public.organizaciones where slug = 'nexus-pro') then
    raise exception 'No autorizado: ... es exclusiva de la organización nexus-pro'
      using errcode = '42501';
  end if;
end if;
```

(función 5 usa `mi_rol() is distinct from 'admin'` en vez de `mi_rol() is null`, para exigir
admin específicamente).

- `auth.role()` lee el GUC `request.jwt.claim.role` que PostgREST pone por petición — funciona
  igual bajo DEFINER o INVOKER, a diferencia de `current_user`/`session_user` (que bajo DEFINER
  siempre son el dueño de la función).
- `session_user <> 'postgres'` exime el acceso directo vía Management API/SQL Editor/migraciones
  (confirmado contra `pg_stat_activity`: toda conexión PostgREST llega como `usename=
  'authenticator'`, nunca `'postgres'`).
- `mi_rol()`/`mi_organizacion()` **no se tocaron** (regla #6 de ChatGPT) — se confirmó su
  definición real (`select rol from profiles where id=auth.uid()` /
  `select us.organizacion_id from profiles p join usuarios_sistema us on ... where p.id=auth.uid()`)
  y se usaron tal cual.

### 3) Matriz actor × RPC × permitido/denegado

Dos partes, con evidencia distinta cada una — juntas cubren toda la matriz mínima que pidió
ChatGPT:

**(A) Cross-org / anon / service_role — probado con clones desechables del guard, DENTRO de
`BEGIN...ROLLBACK` contra PRODUCCIÓN, sin persistir nada.**

Nota de metodología (ya documentada en el `.sql`, se repite aquí porque es relevante para leer
la tabla): la herramienta `execute_sql` de este entorno se conecta SIEMPRE como
`session_user='postgres'` — exactamente el tipo de acceso que la cláusula
`session_user <> 'postgres'` del guard exime a propósito. Probar el guard COMPLETO desde esta
herramienta daría "permitido" para cualquier actor, sin que eso sea un bug — es que la
herramienta de prueba ES el tipo de acceso exento. Para probar la parte que sí importa para
tráfico real (PostgREST, que SIEMPRE llega como `session_user='authenticator'`, nunca
`'postgres'`), se crearon 2 funciones clon **idénticas al guard real pero SIN esa cláusula**
(`_test_guard_anyrole` para el patrón de las funciones 1-3, `_test_guard_adminonly` para la
función 5), otorgadas a `anon/authenticated/service_role`, ejercitadas con fixtures reales
(un admin y un agente de `nexus-pro`, un admin de `bayolsale` — organización real,
`c6e4b954-45ee-46b9-ba94-ae1cbbcc7e10`), y luego todo revertido con `ROLLBACK` — confirmado
después con consultas de conteo que no quedó ningún rastro (0 filas, 0 funciones).

| Actor | Guard "cualquier rol nexus-pro" (fns 1-3) | Guard "admin nexus-pro" (fn 5) |
|---|---|---|
| **admin `nexus-pro`** | ✅ OK — permitido | ✅ OK — permitido |
| **agente `nexus-pro`** | ✅ OK — permitido | ❌ DENEGADO — "exclusiva de administradores de nexus-pro" |
| **admin de OTRA org (`bayolsale`)** | ❌ DENEGADO — "exclusiva de nexus-pro" | ❌ DENEGADO — "exclusiva de administradores de nexus-pro" |
| **anon** (sin sesión) | ❌ DENEGADO — "exclusiva de nexus-pro" | ❌ DENEGADO — "exclusiva de administradores de nexus-pro" |
| **service_role** | ✅ OK — permitido | ✅ OK — permitido |

Esto es exactamente la matriz mínima que pidió ChatGPT: admin `nexus-pro` pasa; agente
`nexus-pro` pasa donde el frontend lo necesita (NCF/recibos) y NO donde no (diagnóstico); admin
de otra organización **denegado en las 2 clases de función**; `anon` denegado; `service_role`
siempre permitido.

**(B) Estado ACL hoy sin el guard aplicado — la evidencia de por qué hace falta.** Con las
mismas fixtures (mismo admin real de `bayolsale`, mismo `set_config` de rol/sub, esta vez SIN
ningún guard interno de por medio, solo la ausencia total de guard que existe hoy en las 5
funciones reales), se confirma que un admin real de otra organización hoy:
- puede ejecutar `siguiente_ncf`/`next_recibo`/`next_recibo_anio` (su ACL a nivel
  `authenticated` ya lo permite, `has_function_privilege('authenticated',...)` → `true` en
  las 5) — sin ningún filtro por organización.
- puede leer `seguros_diagnostico_financiero()` completo — contadores financieros de una
  correduría de seguros que no es la suya.

Esta es la brecha real vigente en producción hoy, la que el guard cierra.

### 4) Prueba de compatibilidad con facturación automática — contra producción, real, hoy

`crear_factura_auto_tx` **no llama** a ninguna de las 4 funciones con guard nuevo (tiene su
propia lógica inline de NCF sobre `secuencias_ncf`) — cero riesgo de interacción entre el
guard y el flujo automático. Confirmado además con una llamada real, completa, como
`service_role`, dentro de `BEGIN...ROLLBACK` contra producción (sin tocar el `.sql` de
hardening todavía, exactamente el estado de hoy):

```sql
SELECT public.crear_factura_auto_tx(
  '<cliente real existente>'::uuid, 'TEST CLIENTE — prueba de compatibilidad 2A', 'PLAN-TEST',
  null, '2099-02', 2, 2099, 1000.00, 0, 0, 1000.00, 'B02', '2099-02-20'::date, 1000.00
);
```
→ `{"ok":true,"ncf":"B0200000609","factura_id":"b05ab4ba-...","referencia":"AUTO-2099-02-b05ab4ba"}`

Factura completa creada de punta a punta (NCF consumido de `secuencias_ncf` — B02 estaba en 608,
el resultado fue el 609 correcto — más el asiento contable correspondiente). Confirmado después
del `ROLLBACK` que nada persistió: 0 facturas con `periodo` de prueba, 0 asientos, y
`secuencias_ncf.B02.ultimo_numero` de vuelta en 608 exacto (la tabla del contador es una fila de
tabla normal, no una `SEQUENCE` de Postgres — por eso el `ROLLBACK` sí revierte el consumo, sin
quemar ningún NCF real).

Esto prueba: (1) el flujo `service_role`/`run_auto_facturacion()` sigue funcionando exactamente
igual con el REVOKE de `anon`/`PUBLIC`/`authenticated` aplicado (el GRANT a `service_role` no se
toca); (2) el propio RLS-a-nivel-de-tabla de `secuencias_ncf` (la función es `SECURITY INVOKER`)
ya le negaba la fila a un actor sin permisos reales sobre esa tabla — mitigación incidental que
existía antes de este hardening, no depende de él, pero tampoco lo reemplaza (el EXECUTE abierto
seguía siendo innecesario).

### 5) Plan de rollback

El `.sql` trae, comentado al final, los 5 `CREATE OR REPLACE FUNCTION` con los cuerpos EXACTOS
capturados en vivo el 2026-08-11 (antes de este hardening) vía `pg_get_functiondef`. Para
revertir: descomentar y ejecutar ese bloque completo.

**Corrección importante ya incorporada al bloque** (consecuencia directa de §0): el rollback
original restauraba `GRANT EXECUTE ... TO PUBLIC, anon, authenticated` para las 3 funciones de
NCF/recibos y para el diagnóstico — eso habría sido una **regresión** respecto al baseline real
de producción (que ya no incluye `anon`/`PUBLIC` para esas 4), no una vuelta al estado real. El
bloque quedó corregido: esas 4 solo restauran el CUERPO (quitan el guard interno), sin tocar su
ACL, que se queda en `authenticated + service_role` (el estado real de hoy). El único
`GRANT ... TO PUBLIC, anon, authenticated` que el rollback sí restaura es el de
`crear_factura_auto_tx`, la única de las 5 que de verdad tenía ese ACL abierto.
