## ChatGPT — 2026-09-15 22:00 RD

Se implementó la primera versión operativa del módulo **Novedades** dentro del flujo de Clientes, autorizada por el dueño con “Exactamente vamos hacerlo”. El objetivo es sustituir la pestaña conceptual **En proceso** por una bandeja única de asuntos pendientes del cliente y alimentar posteriormente un reporte de WhatsApp de novedades del ciclo.

### Decisión funcional

La barra de Clientes conserva la estructura existente, pero `En proceso` pasa visualmente a llamarse **Novedades**. El identificador legado `proceso` se mantiene como alias interno para no romper accesos existentes del Dashboard u otros enlaces.

Estados de Novedades:
- `POR_ACTIVAR`
- `EN_GESTION`
- `EN_RIESGO`
- `POR_RETIRAR`
- `RESUELTO`

Regla crítica: **el sistema nunca retira automáticamente un cliente por falta de pago**. La automatización solamente puede colocar el caso en `EN_RIESGO`. Pasar a `POR_RETIRAR` es una decisión humana y la salida definitiva debe confirmarse por el flujo operativo correspondiente.

### Base de datos

Migración remota aplicada: `20260916014815 clientes_novedades_operativas`.

Se creó `public.cliente_novedades` con historial persistente, origen manual/automático, prioridad, seguimiento, estado, fecha de inicio, resolución y metadata. Se agregaron índices, RLS por organización Nexus Pro y protección contra duplicar una misma novedad automática abierta para un cliente.

Se crearon funciones internas para sincronizar novedades automáticas:
- `novedad_auto_upsert(...)`
- `novedad_auto_resolver(...)`
- `novedades_sync_automaticas_core()`
- `novedades_sync_automaticas()`

La sincronización automática hace dos cosas inicialmente:
1. Todo cliente activo con `estado_cliente='EN_PROCESO'` aparece como `EN_GESTION`, reutilizando `motivo_proceso`, `pendientes_proceso`, `otro_pendiente_detalle`, `nota_proceso` y prioridad existentes.
2. Los atrasos se calculan con el mismo criterio FIFO usado por la cobranza WhatsApp: crédito acumulado en `clientes.pagado` contra facturas no anuladas, en orden de período. Un saldo vencido real crea/actualiza `EN_RIESGO`; cuando desaparece, la novedad automática se resuelve sin borrar historial.

No se creó automatización de `POR_ACTIVAR` basada en número de póliza porque hoy ese dato no distingue de forma fiable una activación pendiente. `POR_ACTIVAR` queda disponible para registro manual hasta tener una señal de negocio inequívoca.

Backfill inicial comprobado:
- 10 novedades automáticas `EN_GESTION` abiertas.
- 15 novedades automáticas `EN_RIESGO` abiertas.
- 5 clientes tienen más de un asunto abierto simultáneo; se conserva el modelo por asunto, no se fusionan problemas distintos silenciosamente.

Cron creado:
- `novedades-sync-hourly`
- `17 * * * *`
- activo

### Seguridad

Después de la migración se ejecutó el Security Advisor. Los helpers internos SECURITY DEFINER aparecieron inicialmente ejecutables por roles que no los necesitaban. Se corrigió con la migración remota `20260916015622 clientes_novedades_security_hardening`:
- `novedad_auto_upsert`, `novedad_auto_resolver`, `novedades_sync_automaticas_core` y el trigger helper quedaron sin EXECUTE para `PUBLIC`, `anon` y `authenticated`.
- Solo `novedades_sync_automaticas()` permanece ejecutable por `authenticated`; valida rol y organización antes de llamar al core.
- Consulta de privilegios posterior confirmó que, entre esos helpers, únicamente ese wrapper conserva EXECUTE para `authenticated`.
- El Security Advisor posterior ya no lista los helpers internos de Novedades como ejecutables por `anon`. Los demás avisos mostrados pertenecen a funciones/tablas preexistentes y no fueron modificados en este trabajo.

Se generó accidentalmente un registro de migración no-op `20260916015233 noop_check_nov` con `select 1;`. No produjo cambios de esquema ni datos. Se añadió también al repositorio para evitar drift del historial de migraciones.
