### RPC / triggers

| Función | Qué hace |
|---|---|
| `pos_fin_amortizacion(capital, metodo, n, fase1, tasa1, tasa2, frecuencia, primera_fecha)` | Única fórmula: capital/n (ajuste de centavos en la última); interés `plano` = capital × tasa, `saldo` = saldo × tasa; fase 1 usa tasa1, el resto tasa2 (fase1 = 0 → todo tasa1). |
| `pos_fin_amortizacion_plan(capital, plan_id, primera_fecha)` | Igual, leyendo el plan. Sirve para simular en pantalla. |
| `pos_fin_aprobar_solicitud(solicitud_id, nota, operacion_id, caja_id, almacen_id)` | admin/gerente. Valida plan, inicial mínima, ítems (importe = precio × cantidad y suma = precio_total), crea la venta a crédito por `pos_registrar_venta_atomica` (inicial efectivo/transferencia/tarjeta + `credito_monto` = capital, factura `CR…`), crea el financiamiento con `pos_fin_crear_financiamiento_v2`, asienta la venta (`pos_reconstruir_asiento_venta`), marca la solicitud y deja evento `aprobacion`. Idempotente (reaprobar devuelve lo mismo). |
| `pos_fin_crear_financiamiento_v2(venta_id, plan_id, primera_fecha, solicitud_id, descripcion)` | Cuotas con capital/interés, `codigo FN-`, `interes_total`, contrato renderizado y congelado, token de firma. |
| `pos_fin_rechazar_solicitud(id, motivo)` | Sin efectos secundarios. |
| `pos_fin_registrar_pago_v2` (extendida) | Reparto **mora → interés → capital**; asiento D 1101/1102 · H 1103 capital · H 4102 interés · H 4103 mora; caja o banco. |
| `pos_fin_reversar_pago` (extendida) | Revierte también el interés (D 4102). |
| `pos_fin_condonar_mora(cuota_id, motivo)` | `mora_exenta`, evento `condonacion_mora`, recalcula la cuota. |
| `pos_fin_mora_calculada` / `pos_fin_mora_total` | Mora del plan (fija / % de la cuota / ninguna, con gracia); fallback al % global de `pos_config` para financiamientos sin plan. |
| `pos_fin_caja_abierta(lock)` | Caja abierta del usuario aceptando `auth.uid()` **o** `mi_usuario_id()` (ver hallazgo). |
| Triggers | `pos_fin_cuota_defaults` (capital = monto − interés si no viene), `pos_fin_solicitud_before_insert` (código SC-), `pos_fin_solicitud_guard_update` (no se puede poner `aprobada` fuera de la RPC; decididas son inmutables). `pos_fin_validar_pago_insert` y `pos_fin_recalcular_cache` reescritos (legado intacto cuando la bandera está apagada y no hay plan). |

## Hallazgos durante el QA (corregidos en 14b/14c)

1. `pos_credito_eventos.tipo` tenía un CHECK cerrado → ampliado con `aprobacion` y `condonacion_mora`.
2. **Bug preexistente del POS**: el navegador guarda `pos_cajas.usuario_id = auth.uid()` (`authUidPOS`) pero
   `pos_fin_registrar_pago_v2` / `pos_fin_reversar_pago` buscaban la caja por `mi_usuario_id()`
   (`usuarios_sistema.id`). En STUDIO ambos ids son distintos → cobrar cuotas en efectivo por RPC habría
   fallado siempre con `FIN_CAJA_CERRADA`. Resuelto con `pos_fin_caja_abierta`. Ojo ChatGPT: la madre tiene el
   mismo código; hoy no le afecta porque el POS no llama a esas RPC.
3. La venta creada por la RPC no tenía asiento (el trigger de `pos_ventas` solo corre en UPDATE). La RPC ahora
   llama a `pos_reconstruir_asiento_venta`.
4. `pos_cuentas_bancarias` no tiene trigger `set_organizacion_id`: hay que enviar `organizacion_id` al insertar.
