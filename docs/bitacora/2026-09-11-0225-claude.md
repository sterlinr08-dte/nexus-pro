# Animación del visto al leerse. Y por qué "el cliente está escribiendo" no se puede hacer

El dueño pidió dos animaciones: **"cuando el cliente está escribiendo"** y **"en leído"**.

Una se puede y está hecha. La otra **no tiene dato detrás**, y conviene que quede escrito para que
nadie la vuelva a prometer.

## 1. "El cliente está escribiendo" — no hay dato

Busqué `typing`, `composing`, `escribiendo`, `is_typing` en Edge Functions, migraciones, frontend e
`index.html`: **cero referencias**.

El webhook (`supabase/functions/whatsapp-webhook/index.ts:284`) solo mapea tres eventos de estado:

```
"message.delivered" -> entregado
"message.read"      -> leido
"message.failed"    -> fallido
```

Más los mensajes entrantes. **No llega ningún evento de "escribiendo"**, y no es una carencia del
código: la API de WhatsApp de Meta no envía al negocio el estado de escritura del cliente. El dato no
existe en el canal.

Se podría *fingir* —animar unos puntitos al azar— pero eso sería mostrarle al dueño una información
falsa sobre lo que está haciendo un cliente. No se hace.

**Lo que sí existiría como alternativa**, en dirección contraria: que el cliente vea "escribiendo…"
mientras el agente redacta. Meta añadió indicadores de escritura que el *negocio* puede emitir. **No lo
he verificado** contra la documentación de Meta ni contra lo que expone Zernio, y tocaría la Edge
Function de envío, así que queda solo apuntado.

## 2. "En leído" — sí, y el dato llega solo

Esto sí está resuelto de raíz:

- el webhook recibe `message.read` y escribe `estado = 'leido'`;
- el frontend está suscrito por Realtime a `whatsapp_hilo_mensajes` con `event:'*'`
  (`parches-whatsapp-inbox.js:1424`), así que el cambio de estado repinta solo.

Así que la animación se dispara sola cuando el cliente lee de verdad.

### Dónde se anima, y dónde NO

La animación va sobre el `<span>` del visto, **nunca sobre la burbuja**. Las capas 22
(`aura-safari-fix`) y 24 apagan `animation`, `transition` y `transform` en `.nxWaBub` y `.nxWaBubWrap`
a propósito, por artefactos de iOS Safari. **Eso no se toca.** Es justo el terreno que ya provocó el
rollback del rediseño de fases 1–4.

### Solo la transición real

El estado anterior de cada mensaje se guarda en un `Map` y no en el `dataset` del nodo, porque
`pintar()` reconstruye el `innerHTML` y el dataset se pierde. Sin eso, **cada refresco de Realtime
volvería a animar todos los mensajes ya leídos**, que es exactamente el tipo de parpadeo que se quiere
evitar.

Comprobado:

```
1er pintado, ya leido      ->  no anima
refresco, sigue leido      ->  no anima
1er pintado, entregado     ->  no anima
el cliente lo lee          ->  ANIMA
refresco posterior         ->  no anima
mensaje entrante           ->  no anima
```

Respeta `prefers-reduced-motion`.
