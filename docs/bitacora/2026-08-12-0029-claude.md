### 2. Matriz de acceso — resultado y NOTA METODOLÓGICA IMPORTANTE

**Hallazgo antes de probar, que cambió el método:** el conector MCP de Supabase de esta sesión SIEMPRE
se conecta como `session_user='postgres'` literal (confirmado con `select session_user`). Intenté
`SET SESSION AUTHORIZATION anon/authenticated` para simular una sesión real no-Postgres y Postgres lo
rechazó (`permission denied to set session authorization`) — en este proyecto administrado, el rol
`postgres` **no** tiene `rolsuper=true` (confirmado: `rolsuper:false`), así que no puedo cambiar
`session_user` desde esta herramienta. Consecuencia real: el guard de estas 5 funciones confía
explícitamente en `session_user='postgres'` como bypass — así que **cualquier llamada mía vía SQL
directo, sin importar qué JWT falsee con `set_config`, va a pasar el guard igual**, porque nunca dejo
de ser `postgres` a nivel de sesión. No es un hueco de seguridad (quien tiene acceso Postgres directo
ya tiene más poder que cualquier RLS), es una limitación de ESTE método de prueba.

Por eso probé el guard de la única forma honesta posible sin ejecutar las funciones de escritura como
otro rol: **evalué el predicado exacto que usa el guard** (`mi_rol()`/`mi_organizacion()`, funciones

### 3. `crear_factura_auto_tx` como service_role — camino feliz completo, dentro de ROLLBACK

un contador que nadie lee. Lo dejo documentado por honestidad, no porque tenga impacto.
